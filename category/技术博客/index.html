通道全景：先搞清楚谁在哪个线程

关键事实：原生侧的 handleMethodCall 默认在主线程被调用。这意味着两件事：Dart 调用过来时你在主线程；你在 handler 里做任何耗时操作（读数据库、同步网络、大 JSON 解析），都是在卡 Flutter 的 UI 线程——是的，原生主线程和 Flutter UI 线程在渲染节拍上是一体的，卡一边等于卡两边。

iOS 数据持久化选型：从 UserDefaults 到数据库的那条线

场景 方案 关键理由
用户偏好/开关（<几KB） UserDefaults 同步读、简单，但注意下面第三节
密钥/令牌 Keychain 加密、备份可控、删 App 可留
单一大对象缓存（接口结果） 文件 + Codable（Caches 目录） 可整体失效、不进备份

大量小对象频繁读写 SQLite 系，别用 plist 单文件全量读写的代价见第三节

鸿蒙 ArkUI 长列表实战：LazyForEach 的正确打开方式

鸿蒙 App 里最容易写出性能问题的地方，就是一个塞了几千条数据的长列表。新手期我把 ForEach 用到底，列表一长就掉帧、内存曲线爬得像心电图。改到 LazyForEach 之后才明白：ArkUI 的列表优化不是换个 API 的事，是一整套"数据源 + 复用 + 缓存"的纪律。这篇把这套东西一次讲透。

ForEach 的原罪：一次建完

ForEach 的语义是"给数组每项都当场建组件"。三千条数据的评论列表，ForEach 会在首帧前把三千个组件全量构建出来——哪怕用户只看得到七八条。

// ❌ 大列表用 ForEach: 首帧卡、内存高
List() {
  ForEach(this.comments, (item: Comment) => {
    ListItem() { CommentRow({ data: item }) }
  }, (item: Comment) => item.id.toString())
}

iOS 键盘避让踩坑记：表单页的那些疑难杂症

键盘看似 iOS 里最小的交互，但做过复杂表单的人都知道它多能折腾：输入框被挡、避让过头、返回页面滚动位置乱跳、第三方键盘高度漂移。这篇把表单页键盘相关的坑汇总一遍，附我们最终落地的避让方案。

基础：通知里有你要的全部信息

键盘弹出/收起有四个通知，关键是拿全两个字段——键盘 frame 和动画时长曲线：

- (void)keyboardWillChange:(NSNotification *)note {
    CGRect endFrame = [note.userInfo[UIKeyboardFrameEndUserInfoKey] CGRectValue];
    NSTimeInterval dur = [note.userInfo[UIKeyboardAnimationDurationUserInfoKey] doubleValue];
    UIViewAnimationCurve curve = [note.userInfo[UIKeyboardAnimationCurveUserInfoKey] integerValue];

    // 转换到当前 view 坐标系（别拿屏幕坐标直接算，分屏下会翻车）
    CGRect local = [self.view convertRect:endFrame fromWindow:nil];
    CGFloat overlap = MAX(0, CGRectGetMaxY(self.view.bounds) - CGRectGetMinY(local));

    // 动画要跟系统同曲线，否则键盘飞你的内容不动，观感割裂
    [UIView animateKeyframesWithDuration:dur delay:0 options:0 animations:^{
        self.scrollView.contentInset.bottom = overlap;
        self.scrollView.verticalScrollIndicatorInsets.bottom = overlap;
    } completion:nil];
}
